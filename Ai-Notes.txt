## Simulator timing limitation (IMPORTANT)
- The firmware uses Timer2 for the approximately 1 ms scheduler tick because MDB's Timer0 model stalled during earlier testing.
- The simulator is still a debugger model, not a substitute for silicon timing. The suite validates state ordering, LCD lifecycle, trip latching, and recovery behavior; bench validation remains required for exact hardware timing.
- **Timer1 external clock (T1CKI) is NOT modelled** - the simulator reports "W0106-SIM: This device only has partial support for TMR1 peripheral ... timer clock selection is not implemented". Verified 2026-09-21: with RD1 actively driven by an SCL stimulus (`stim <file.scl>`; `print pin RD1` = HIGH/Din) and T1CON correctly set to T1CKI with the 1:4 prescaler (0x27), TMR1L/TMR1H stayed at 0. So a true end-to-end RF frequency-counter test is IMPOSSIBLE in sim, and no stimulus mechanism can fix it - the peripheral model is missing. The suite therefore injects TMR1H/TMR1L directly, which covers the frequency maths, band classification, band-select outputs and TX lock, but not the T1CKI pin, PPS routing, prescaler, or Timer1 overflow path. Do not "fix" this by trying to clock the pin.
- MDB SCL is available even though the harness does not currently need it: `stim <file>.scl` attaches a stimulus (mdb help -> "Stim"), SCL processes run once per instruction cycle *including during `Stepi`*, and the assignment operator for pins/SFRs is `<=` (use `:=` for user variables). `RD1 = '1';` is NOT valid and derailed the simulator with "E0101-SIM: Failed to disassemble instruction".

## Current design
This repository is the active PIC16F18875-I/P linear-amplifier protection controller. Obsolete prototype source files have been removed so they cannot enter the production build.

## Firmware
- **First-dit band switching is implemented** (docs/first-dit-band-detection.md). With no decoded
  band, PTT is latched but the amplifier stays in bypass (STATE_BYPASS_SNOOP, g_snoop_active) while
  the radio's first RF burst is decoded; the band is then remembered (g_band_cache_valid/
  g_band_cache_band) so later PTT drops engage instantly, and the memory is dropped after
  BAND_CACHE_IDLE_TIMEOUT_MS (60 s, needs bench confirmation) of inactivity. BAND_SETTLE_MS (20 ms,
  needs bench confirmation) holds bypass after the decode so the amplifier is never keyed into a
  relay that is still moving. apply_bypass()/release_band_if_cold() enforce the "relays only move
  with the amplifier cold" rule, and g_band_established gates keying: the amplifier never keys
  unless a band is backed by a real measurement or the first-dit memory for this transmission
  (that is what stops it keying on the classifier's 160m no-signal default after a trip
  recovery). New freq_counter API: freq_counter_restore_locked_band(),
  freq_counter_band_confirmed(), freq_counter_measured_band().
- **The remembered band is verified, not trusted (fold-back).** A first-dit engage taken from the
  band memory is a blind decision - at keydown the radio has not started transmitting, so there is
  nothing to measure yet. The remembered band is therefore re-checked against the first usable
  measurement of that same transmission: if the measured band differs for BAND_VERIFY_MS (20 ms),
  the firmware forces bypass FIRST, releases the band, and lets the snoop path re-select the band
  actually being received cold before re-engaging. This is what makes the user's "FirstDit on 160m,
  then immediately change to 80m and key straight away" case safe: the amplifier never amplifies the
  whole first over through the wrong filter. Measured fold-back latency in the simulator: 23 ms.
  The relay selection is never moved while keyed (the verify step bypasses before it unlocks).
- Direct ADC inputs monitor two forward/reflected SWR pairs, temperature, WCS1700 current, input power, and drain voltage. Which channel is which lives ONLY in docs/hardware/PIC16F18875_pin_map.md - never restate that list here.
- ADC configuration (firmware/src/main.c adc_init): 10-bit, right-justified legacy format, VDD-referenced with the internal FVR off. Raw values are consumed directly as plain 0-1023 counts, so at a 5 V rail one count is about 4.88 mV.
- Current-sensor scaling (firmware/src/main.c): zero at raw 512 (2.5 V mid-rail), +511 counts = +70 A, 0 counts = -70 A. The default positive current trip is 40 A (g_thresholds initialiser).
- On PTT release the sequencer unwinds in order - TX off immediately, TX_VCC after the VCC delay, then TX_BIAS - and the band is released only once every TX output is confirmed inactive (release_band_if_cold()). An engage still in progress when PTT releases is therefore unwound, not completed; the old "engages complete, then unsequence" description is obsolete (see bugfixes.md 2026-09-21).
- SWR trips, power scales, drain/input thresholds, 10 kOhm NTC B-value profile, sequencer timing, and output polarities are user-configurable from the 1602 LCD menu.
- Hardware comparators combine at INPUT_HARD_FAULT for independent overdrive, drain-peak, and overcurrent protection.
- The sequencer runs TX, TX_VCC, and TX_BIAS with two configurable inter-stage delays, defaulting to 20 ms.
- The LCD is a 1602 driven in 4-bit parallel mode by firmware/src/lcd_parallel.c; there is no I2C backpack. firmware/include/lcd_i2c.h is the (legacy-named) interface header for the LCD plus internal EEPROM. Pin assignments: see the single-source-of-truth rule above.
- Menu settings and the last display page are stored in the PIC's internal EEPROM in a versioned, checksummed record; no external EEPROM module is used.

## Simulation
- Both build configurations link to the SAME `out/My_Pic_Project/default.elf`. After a Release build the debug ELF (and the symbols the harness reads with `print <var>`) is gone, and Ninja says "no work to do" for Debug, so delete the ELF and rebuild Debug before running the simulator tests: `rm -f out/My_Pic_Project/default.elf && cmake --build _build/My_Pic_Project/debug -j4`.
- The firmware can be simulated instruction-accurately on the exact PIC16F18875 using MPLAB X's headless `mdb` debugger (gpsim does NOT support this device - its newest PIC16F1 parts are the 1788/1823/1825/1847 family, missing this chip's ADCC/CLC peripherals).
- Cross-platform tooling: macOS uses `tools/simulate/*.sh`, Windows uses `tools/simulate/*.ps1` (same behaviour). `cmake/My_Pic_Project/default/.generated/toolchain.cmake` and `.generated/rule.cmake` auto-detect XC8/DFP pack locations per-OS (macOS: `$HOME/tools/microchip/...`; Windows: `C:/Program Files/Microchip/xc8/...` and `%USERPROFILE%/.mchp_packs`, since `$ENV{HOME}` isn't set on Windows) - no manual cache overrides needed on either OS.
- IMPORTANT build-flag fix (2026-09-15): `cmake/My_Pic_Project/default/user.cmake` used to unconditionally append `-Os`, which silently overrode the Debug preset's `-O0` (last `-O` flag wins) - so "debug" builds were actually optimized, breaking mdb breakpoints/symbols (tiny functions got inlined, statics got stripped). Now `-Os` only applies via `$<$<CONFIG:Release>:-Os>`. If mdb breakpoints on functions/statics mysteriously don't resolve again, check this file first.
- macOS setup: `brew install --cask mplabx-ide mplab-xc8`.
- Windows setup: install the full MPLAB X IDE (not just MPLAB IPE) so `mdb.bat` (under `mplab_platform/bin`) is present. The already-installed VS Code extensions `microchip.mplab-core-da` (Debug Adapter for MPLAB) and `microchip.mplab-data-visualizer` give a GUI debug/scope experience but both ultimately drive the same `mdb`/simulator engine, so scripted simulation doesn't require them.
- `tools/simulate/build_firmware.sh` (macOS) / `build_firmware.ps1` (Windows) builds firmware locally into `_build/My_Pic_Project/sim` / `out/My_Pic_Project/default.hex`.
- `tools/simulate/run_sim.sh` / `run_sim.ps1 [scenario.mdb]` builds, then launches `mdb` against device `PIC16F18875` with the hex programmed, filtering the benign `W0106-SIM` TMR1/3/5 warnings (see below) out of the output. With no argument it's an interactive `mdb` session; with a scenario file it runs those commands then exits. `write pin <name> high|low|<N>v` to drive inputs, `print pin <name>` to read outputs, `Stepi <count>` to single-step, `break <function>`/`break <file>:<line>` + `Run`/`Continue`/`Halt` for real breakpoint-based debugging, `Stopwatch [nror]` for real simulated elapsed time. Example scenarios: `tools/simulate/scenarios/boot_smoke.mdb`, `ptt_cycle.mdb`.
- mdb command files do not support `;`/`#` comment lines - an invalid line aborts the rest of the script, so keep scenario files to plain commands only.
- A VS Code GUI debug session (breakpoints/variables/watch/registers, no terminal) is available via `.vscode/launch.json`'s "Simulate PicAmpControl (Debug)" config, using `microchip.mplab-core-da` against `Simulator`/`PIC16F18875`. Requires `out/My_Pic_Project/default.elf` to exist (build first). Pin/register live-watch: add `PORTA`/`PORTB`/`PORTC`, `LATA`/`LATB`/`LATC`, `TRISA`/`TRISB`/`TRISC` (or bitfields like `PORTCbits.RC5`) to the Watch panel manually - there is no file-based way to pre-seed Watch expressions.
- `main.c` explicitly clears `ANSELC` so RC0/RC3-RC7 operate as digital I/O; keep this initialization when changing the port map.
- Benign, expected simulator noise: `W0106-SIM: This device only has partial support for TMR1/TMR3/TMR5 peripheral...` on every reset. Firmware never touches T1CON/T3CON/T5CON; this is just `mdb`'s partial clock-source-mux model for those timers at their POR default state, not a real firmware/silicon issue - safe to ignore (already filtered out by run_sim.sh/.ps1).
- FIXED (2026-09-15, see bugfixes.md): the ADC ISR used to immediately re-arm the next conversion (with a blocking `__delay_us`) right after each conversion completed, entirely inside `timer0_isr()`. In simulation this created a back-to-back interrupt chain that fully starved the main loop - `update_tx_sequence()`/`update_protection_state()` never ran even once after 30+ simulated seconds. Fixed by only re-arming once per Timer0 tick (~1 ms) instead of immediately; verified main-loop breakpoints now hit normally. If future simulation runs show the CPU stuck at the interrupt vector address on every `Halt` with continuous `W0223-ADC` spam, that class of bug is back.
- To simulate a steady-state-then-PTT-drop scenario without spurious protection faults, drive plausible idle ADC voltages before running: `write pin RA0/RA1/RA2/RA3 0v` (SWR fwd/ref, both pairs), `write pin RA5 2.5v` (temp), `write pin RB1/RB2/RB3 0v` (current/overdrive/drain), `write pin RB4 low` (hw overcurrent fault, active-high). PTT (`RC0`) is active-low; hold `high` for idle/steady-state, then `low` to assert. Without explicit stimulus, floating ADC inputs read as very low/high and spam `W0222/W0223-ADC` over/underflow warnings (cosmetic) but can also cause `swr_trip()` etc. to behave unpredictably.
- The simulator suite runs eleven scenarios in one MDB session and emits per-scenario CSVs and graphs under `_build/My_Pic_Project/sim/csv/` and `_build/My_Pic_Project/sim/graphs/`. The first-dit proof is a separate session (`tools/simulate/test_first_dit.py`, `--csv` to dump its samples) and shares the band-selection invariant checks in `tools/simulate/first_dit_invariants.py` with the suite.
- Injecting snoop RF only *before* PTT models a radio that is silent while transmitting. The tick resets TMR1 every 10 ms, so the injected measurement goes stale and the firmware correctly stays in bypass. Keep the band frequency injected for the whole keyed window (the suite does this for 40m now; see bugfixes.md 2026-09-21).
- mdb cannot write a C variable by name in this version (`write g_x 1` fails with `For input string: "<addr> "`, and `print /a g_x` fails the same way). Fault injection into firmware state works via the address: read it from `out/My_Pic_Project/default.sym` (line format `_g_name <hexaddr> 0 BANKn <size>`, e.g. `_g_band_cache_idle_ms B4 0 BANK1 1`) and use `write /r 0x<addr> <lo> <hi>` for a 16-bit value (little-endian, one byte per word) or `write /r 0x<addr> <byte>` for a bool/enum. Addresses move on every rebuild, so parse the .sym at run time (test_first_dit.py does).
- Run tests with `./run_tests.sh` or `ctest --test-dir _build/My_Pic_Project/debug --output-on-failure > /tmp/pac_ctest.log 2>&1` (see TESTING.md). A green run ends with `100% tests passed`; the suite prints `PTT suite passed: 11 scenarios in one MDB session` and the first-dit proof prints `FIRST-DIT PROOF PASSED: ...`. Both together take roughly 3 minutes.
- CTest registers two tests (cmake/My_Pic_Project/default/user.cmake): `PTT_SequencerAndTripSuite` (labels `sim;suite`, ~2.5 min, runs `run_suite_with_watchdog.py --timeout 300`) and `FirstDit_BandDetectionAndHotSwitchGuards` (labels `sim;first-dit`, ~20 s, runs `tools/simulate/test_first_dit.py`). Select with `-R FirstDit`, `-R PTT_Sequencer`, or `-L sim`; never run the two concurrently (both own MDB, and the suite launcher kills stray MDB processes). The suite is Python 3 only and configuration now fails if the discovered interpreter is not Python 3; `PYTHON_EXECUTABLE` is cached, so clear it with `-U PYTHON_EXECUTABLE` when reconfiguring an existing build directory.

## Device memory usage

- To check current % free: download it from the latest release (`gh release download <tag> -p memoryfile.xml`) and read `<memory name="program">`/`<memory name="data">` `used`/`free`/`length` (program = flash words, data = RAM bytes).
- FLASH IS TIGHT (2026-09-21): Release (shipping) uses 6899/8192 words = 84.2% used (15.8% free); the Debug build that the simulator/tests load uses 8135/8192 = 99.3% used, because user.cmake deliberately compiles Debug with -O1 (not -Os) so mdb can resolve symbols and breakpoints.
