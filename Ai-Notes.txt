## Current design
This repository is the active PIC16F18855-I/SP linear-amplifier protection controller. Obsolete prototype source files have been removed so they cannot enter the production build.

## Firmware
- Direct ADC inputs monitor two forward/reflected SWR pairs, temperature, WCS1700 current, input power, and drain voltage.
- SWR trips, power scales, drain/input thresholds, 10 kOhm NTC B-value profile, sequencer timing, and output polarities are user-configurable from the 1602 LCD menu.
- Hardware comparators combine at INPUT_HARD_FAULT for independent overdrive, drain-peak, and overcurrent protection.
- The sequencer runs TX, TX_VCC, and TX_BIAS with two configurable inter-stage delays, defaulting to 20 ms.
- The LCD uses a PCF8574 backpack driven with software I2C on RC3/RC4 by firmware/src/lcd_i2c.c.
- Menu settings and the last display page are stored in the PIC's internal EEPROM in a versioned, checksummed record; no external EEPROM module is used.

## Display
- The default status page shows post-filter forward power as PEP or RMS and a full-width `-`/`.` PEP bar.
- A second status page shows a PEP bar with temperature in degrees C.
- PEP decay is user-configurable and defaults to 500 ms.

## Simulation
- The firmware can be simulated instruction-accurately on the exact PIC16F18855 using MPLAB X's headless `mdb` debugger (gpsim does NOT support this device - its newest PIC16F1 parts are the 1788/1823/1825/1847 family, missing this chip's ADCC/CLC peripherals).
- Cross-platform tooling: macOS uses `tools/simulate/*.sh`, Windows uses `tools/simulate/*.ps1` (same behaviour). `cmake/My_Pic_Project/default/.generated/toolchain.cmake` and `.generated/rule.cmake` auto-detect XC8/DFP pack locations per-OS (macOS: `$HOME/tools/microchip/...`; Windows: `C:/Program Files/Microchip/xc8/...` and `%USERPROFILE%/.mchp_packs`, since `$ENV{HOME}` isn't set on Windows) - no manual cache overrides needed on either OS.
- macOS setup: `brew install --cask mplabx-ide mplab-xc8`.
- Windows setup: install the full MPLAB X IDE (not just MPLAB IPE) so `mdb.bat` (under `mplab_platform/bin`) is present; MPLAB X for VS Code is just a UI wrapper around the same `mdb` engine, so it isn't required for scripted simulation.
- `tools/simulate/build_firmware.sh` (macOS) / `build_firmware.ps1` (Windows) builds firmware locally into `_build/My_Pic_Project/sim` / `out/My_Pic_Project/default.hex`.
- `tools/simulate/run_sim.sh` / `run_sim.ps1 [scenario.mdb]` builds, then launches `mdb` against device `PIC16F18855` with the hex programmed. With no argument it's an interactive `mdb` session (`write pin <name> <0/1/xV>` to drive inputs, `print pin <name>` to read outputs, `Stepi <count>` to advance); with a scenario file it runs those commands then exits. Example: `tools/simulate/scenarios/boot_smoke.mdb`.
- mdb command files do not support `;`/`#` comment lines - an invalid line aborts the rest of the script, so keep scenario files to plain commands only.
- Known finding from simulation (not yet fixed): `ANSELC` is never cleared in `main.c` (only `ANSELA`/`ANSELB` are), so RC0/RC3-RC7 stay in their power-on-reset analog-capable state as far as the pin model is concerned. Outputs (RC5-7) still drive correctly because TRIS overrides ANSEL for output pins, but the digital input path used for the software-I2C bus (RC3/RC4) and future digital reads on RC0 may be affected on real silicon - worth a bench check.

## CI / release
- .github/workflows/firmware-build.yml builds on every push/PR to main on a self-hosted Windows runner (XC8 + Ninja) and packages `.hex`/`.elf`/`.map`/`.xml` plus the pin map (docs/hardware/PIC16F18855_pin_map.md) into a `firmware-<sha>` artifact.
- .github/workflows/auto-release.yml runs after a successful main build, auto-increments a `v0.0.N` tag, and publishes that artifact as a GitHub Release. This is fully automatic - no manual step needed for a normal push to main.
- .github/workflows/release-firmware.yml is the manual fallback (workflow_dispatch) to re-publish an older build's artifact under an existing tag.

## Device memory usage
- `memoryfile.xml` (and `mem.map`) is regenerated by XC8 on every build and is always included in the latest release, so it always reflects the current firmware, not a stale snapshot.
- To check current % free: download it from the latest release (`gh release download <tag> -p memoryfile.xml`) and read `<memory name="program">`/`<memory name="data">` `used`/`free`/`length` (program = flash words, data = RAM bytes).
- As of v0.0.25 (commit 3a49285): program flash 54.2% free (4440/8192 words), data RAM 84.2% free (862/1024 bytes).
